# 皮皮虾 (PPX Agent) 全面评价报告

> 版本：v0.10.2 | 评价日期：2026-08-16 | 评价方式：源码静态审查 + 全量测试 + 配置核查
> 代码规模：src/ 57 个文件 · 6,623 行 | 测试：242 项（239 过 / 0 失败 / 3 跳过）

---

## 一、总评

**综合得分：89 / 100**（与 v0.10.2 历史评分持平，但发现若干环境级与文档级回归风险）

皮皮虾是一个完成度很高的零依赖 Node 智能体内核。它吸收了两大开源项目的精华（HanaAgent 的记忆分层/自愈、TencentDB-Agent-Memory 的四层记忆），用干净自包含的方式重搭，架构上做到了"一切皆插件 + 事件溯源为唯一事实源 + 多引擎可插拔回退"。在**离线可验证的范围内**（测试、代码质量、功能覆盖面），它的工程质量显著高于同规模的手写 Agent 项目。

但本轮评价必须诚实指出：**当前机器的实际运行环境不满足默认底座的硬性要求**，导致"开箱即用"打了折扣；同时 `docs/` 目录已被清空，历史评价与验收文档全部丢失。这两点是本轮最值得警惕的回归项。

## 二、六维度评价

### 1. 功能完整性 —— 92 / 100

**表现：能力覆盖面在同级项目中属于第一梯队。**

| 能力域 | 实现情况 | 依据 |
|--------|----------|------|
| 四层记忆 L0-L3 | 完整 | `src/memory/` 8 文件：l0 原始日志 / l1 高斯衰减事实 / l2 场景聚类 / l3 画像 |
| 检索 RAG | 完整 | `fact-store.js` BM25 + 倒排索引 + bigram 精排 + dense 余弦(可插拔) + RRF 融合 |
| 会话 | 完整 | `session.js` append-only 事件日志 + deriveMessages 投影 + replay/fork |
| 工具系统 | 完整 | 32 个内置工具 + code_act 沙箱 + 自定义工具 + 热挂载 |
| LLM 底座 | 三引擎 | openclaw / dsh(DeepSeek Harness) / http 原生，多 provider 并发健康探测 + 回退 |
| 多模态 | 完整 | 图片注入 image_url 块 + vision provider 路由 |
| OCR | 完整 | 本地 tesseract + 百度云回退 + 扫描件 PDF 自动 OCR |
| 文档加载 | 完整 | txt/md/json/csv/html/pdf 零依赖提取 |
| 编排 | 完整 | 7 模式：single/react/plan-exec/router/blackboard/graph/legion + DAG |
| MCP | 完整 | 零依赖客户端，stdio + HTTP Streamable 双传输 |
| 通道 | 完整 | http(可用) + 飞书 + 微信(加解密/主动推送/加密回包) |
| 安全 | 完整 | Bearer 认证 / SSRF / 命令黑白名单 / 路径穿越 / PII / 注入防护 / 限流 |

**薄弱环节（扣分项）：**

1. **默认底座在当前机器不可用（P0 环境问题）**。`config/ppx.json` 的默认 provider 是 `openclaw`，其 `engines` 声明要求 Node `>=22.22.3`，但本机实际是 **v22.22.2**，差 0.0.1 个补丁版本，`nodeVersionOk()` 会直接判 false，`health()` 返回 false。也就是说**默认引擎在此环境必然降级**。
2. **openclaw/dsh 的工具调用是"半残"状态**。这两个后端是外部进程，无法原生 `tool_calls`，靠 `fence.js` 围栏协议兜底；但代码注释明确承认"openclaw 是完整 agent 运行时，会拒绝围栏协议（视为伪协议）"。实测只有 http 后端（LM Studio 等）能走原生工具循环。这是架构上的一处张力，非纯代码 bug，但影响工具类任务的可靠性。
3. **无 dense embedding 默认**。语义检索依赖可插拔 `embedder`，需要外部 API（配置指向本地 LM Studio 的 embedding 端点），未配置时纯 BM25 兜底。

### 2. 响应质量 —— 84 / 100

**表现：工程侧为"高质量输出"做了大量设计，但缺乏真实端到端验证数据。**

**做得好的：**
- 记忆检索用 BM25 IDF 区分罕见词/常见词 + 时效乘性衰减 + 重要性因子 + LLM 查询扩展 + RRF 融合，召回设计严谨（`fact-store.js`）。
- 上下文裁剪是"信息量感知"的：优先保留含指令/数字/路径/结论的轮次，纯寒暄让位（`_historyPriority`），比纯条数硬截更聪明。
- 工具错误自动重试（`MAX_TOOL_ERROR_RETRY=2`），失败轨迹回喂模型修正。
- 本地意图预判（问候/时间/记忆查询）不走 LLM，省成本且响应快。
- 防注入边界写进了人格文件 `ishiki.md`，不是空口号。

**扣分项：**
- **零真实 E2E 数据**。当前无任何 API key，三个 http provider + embedding 端点全部无法健康探测；openclaw 又受 Node 版本限制。因此"回答准确性/专业性/是否真正理解用户意图"**无法被客观验证**，只能从代码设计上推断。这是最需要补的短板。
- `LLMClient.apiKeyEnv()` 是死代码（恒返回 `undefined`，见 `client.js:303`），导致缺 key 报错里的 `env=...` 永远显示 `?`，诊断信息缺失。

### 3. 语言一致性 —— 95 / 100

**表现：本维度是项目最稳定的一环。**

- 全部注释、工具 description、错误提示、引导文案、配置、README、CHANGELOG 均使用**统一简体中文**，且语气契合人格设定（直接、务实、不废话）。
- 历史乱码已清零：本轮 `grep` 未发现 `�` 替换符或 `??` 残留；`v0.5.1` 曾修复的注释乱码未复发。
- 工具描述语言统一为中文（`notify` 早在 v0.6.2 已英改中）。

**扣分项（轻微）：** 代码标识符仍以英文为主（`_llmWithTools`、`FactStore` 等），但这是工程惯例，不影响一致性；系统提示词对"模型返回 JSON"的指令是中文，与整体风格一致。

### 4. 处理效率 —— 90 / 100

**表现：对零依赖单机场景做了多项实打实的性能优化。**

| 优化点 | 效果 | 依据 |
|--------|------|------|
| 并发健康探测 | 多 provider 秒级跳过不可用项，避免串行 180s 超时 | `_llmWithFallback` |
| 倒排索引 | 记忆检索 O(n) → O(候选) | `fact-store._index` |
| BM25 统计缓存 | 免每查询 O(N) 重算 | `_statsCache` |
| 会话增量落盘 | 消除 1000+ 条会话的写放大 | `session._flush` appendFileSync |
| 工具结果裁剪 | 超 4000 字符截头尾，防上下文撑爆 | `trimToolResult` |
| 上下文预算裁剪 | 条数+token 双上限 | `_trimHistory` |

实测：全量 242 项测试 **56.7s** 跑完，测试隔离用临时目录，不污染生产数据，稳定性好。

**扣分项：** openclaw/dsh 后端伪流式（`supportsStream` 仅 http 为 true），默认底座无打字机效果，长回复体验偏"一次性蹦出"。

### 5. 用户体验 —— 87 / 100

**做得好的：**
- CLI：readline 历史（↑↓）+ `/stop` 中断 + `/reset` 清会话 + Ctrl+C 单次中断 + busy 防重入，交互细节到位。
- Web UI（`web/`，Next.js + TS，node_modules 已装）：聊天 / 场景 / 记忆 / 轨迹 / 统计 多面板，工具调用卡片可视化（⏳调用中→✓完成/✗失败），多会话管理，SSE 流式，深浅主题跟随系统，移动端响应式。
- 缺 key / 缺依赖时报**中文引导**而非原始堆栈（如"请升级 Node 至 >=22.22.3"），对新手友好。

**扣分项：**
- `docs/QUICKSTART.md`、`docs/CONFIG.md` 在 README 中被引用但**实际不存在**（`docs/` 已空），新手上路会踩"链接 404"。
- 环境门槛偏硬：引擎要求 Node 22.22.3/24.15/25.9 三段式，且明示 23 与 24.0-24.14 不支持，版本敏感度高。

### 6. 改进建议（分优先级）

**P0（必须尽快处理）**
1. **解决默认底座不可用**：二选一 —— 把本机 Node 升到 >=22.22.3（或 26.x），或把 `config/ppx.json` 的默认 provider 切到 dsh/http 并配好 key。当前"默认引擎必失败"的状态不能长期存在。
2. **恢复文档**：README 引用的 `QUICKSTART.md`、`CONFIG.md` 缺失，历史评价/验收文档丢失。至少补回 QUICKSTART/CONFIG，重建 `docs/` 基线。

**P1（短期改进）**
3. **补一条真实 E2E 冒烟**：配置至少一个可用 key（LM Studio 本地即可），跑通"对话→工具调用→记忆落盘→重启检索"全链路，把延迟/Token 成本/完成率量化，填上"响应质量不可验证"的空缺。
4. **修 `apiKeyEnv()` 死代码**：让缺 key 报错能显示具体缺哪个 env，而不是恒 `?`。
5. **明确 openclaw 工具调用的取舍**：要么在文档声明"openclaw 底座不支持工具调用，仅纯对话"，要么实现真正的 openclaw 工具桥接，避免围栏协议"名义可用实则被拒"的误导。

**P2（长期优化）**
6. 内置一个零依赖的 dense embedding 兜底（如轻量哈希向量），让语义检索脱离外部 API 也能用。
7. openclaw/dsh 的 SSE 流式接入，恢复默认底座的打字机体验。
8. 补充性能基准测试（千级记忆检索延迟、大会话落盘耗时），把"处理效率"从定性好评升级为量化指标。
